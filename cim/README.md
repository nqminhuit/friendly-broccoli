# cim — CI Management

cim is a standalone Manifest V3 browser extension for monitoring GitHub Actions across multiple GitHub account/repository profiles. The combined dashboard labels and filters loaded runs, expands runs to show their jobs and steps, offers explicit rerun-all and rerun-failed controls for completed runs, and offers a New run form that dispatches `workflow_dispatch` workflows with typed inputs. It does not show live logs or monitor in the background.

## Install and configure

1. Load the `cim/` directory as an unpacked extension in Brave or Chrome (`chrome://extensions`, enable Developer mode, then **Load unpacked**).
2. Open the cim toolbar action and create a connection profile (for example, Personal or Work). Give each profile its own repositories and GitHub personal access token; the same repository can appear in different profiles.
3. Use a fine-grained PAT with **Actions: read** access on every repository in that profile for monitoring. Reruns and New run dispatches additionally require **Actions: write**; New run forms also require **Contents: read** to load workflow files. Never share the token.
4. **Test access** checks the Actions runs endpoint for the selected profile's repositories.

Each profile's PAT is kept in extension session storage by default and is cleared when the browser session ends. **Remember on this device** independently opts that profile into storing the PAT as plaintext in local extension storage; anyone with access to this browser profile can read it. Leaving the password field blank while saving keeps only that profile's current token. **Forget token** clears the selected profile's PAT while retaining its repository list; removing a profile deletes its settings and PAT. Profile names/repositories and the remember choice are stored locally. Opening a private repository's GitHub run page uses the browser's GitHub web session, not the PAT; switch the signed-in GitHub web account there if access requires a different account.

## Monitoring and privacy

New run dispatches a selected `workflow_dispatch` workflow at an editable branch/tag ref (defaulting to that repository’s default branch). The workflow must declare `workflow_dispatch` on its default branch; the form reflects the selected ref’s YAML and supports string, boolean, number, choice, and environment inputs. Reruns re-execute an existing run with its original commit, ref, and actor permissions, while New run starts a new run from current YAML and explicit inputs. The dashboard requests `https://api.github.com` only while it is open and visible. Monitoring uses GET requests; confirmed user-initiated reruns and dispatches use POST and are never automatically retried. It pauses timers and cancels in-flight reads while hidden or closed. Active runs are refreshed about every 10 seconds, otherwise about every 30 seconds, subject to per-profile GitHub rate limits and repository count. Expanded active runs and pending reruns refresh their metadata and latest-attempt jobs; completed details remain in memory until refreshed or reopened. A timed-out, disconnected, or hidden-then-aborted rerun/dispatch request may have reached GitHub, so check GitHub before explicitly enabling another request. Uncertain dispatches show a workflow page link (never a guessed newest run) until you acknowledge after checking GitHub. Dispatched runs pin their exact returned run ID for monitoring until a terminal result; they are not labelled success until GitHub reports completion. GitHub enforces its 30-day and 50-rerun limits. An expired PAT pauses only its profile; inaccessible repositories pause their own automatic reads. Only the newest 30 runs per repository load initially; **Load older runs** follows validated GitHub pagination links. Filters cover loaded history. The service worker only opens/focuses the dashboard and never polls GitHub.

Opening a private run or workflow page uses the browser’s GitHub web session, not the PAT. GitHub API responses are kept only in the open dashboard's memory. No external services, analytics, remote scripts, or credentials in URLs are used. Workflow YAML parsing uses the local `vendor/js-yaml.umd.min.js` artifact only; no background monitoring exists yet and no release workflow is included. Rate limits can temporarily pause refreshes; adjust repository count or wait for GitHub's retry time.

## Tests

Run the focused unit suites with `node --test cim/core.test.cjs cim/dispatch.test.cjs` and the browser smoke tests with `node --test cim/e2e.test.mjs` (skips if Chrome is unavailable; set `CHROME` to its executable path). Existing repository unit regressions: `node --test vtelex/telex.test.js vtelex/macros.test.js bcoin/infill.test.js`.
